# DNS の L7 検知 — 侵入後を前提にした「53番」の見える化

> 正直な適用範囲を先に。ChickenNet は **AD 全体のマイクロセグメンテーション製品ではありません**。
> ここで扱うのは「DNS(53番)という常時開いた通路を、L7(問い合わせの中身と振る舞い)で
> 見える化し、必要なら止める」という **部分適用** です。Kerberos/LDAP/SMB の制御は対象外です
> (将来の検討事項。末尾「対象外と今後」を参照)。

## なぜ DNS を L7 で見るのか

侵入を 100% 防ぐ前提は今や現実的ではありません。重要なのは、侵入された後に攻撃者が
内部で動く段階(偵察・横展開・持ち出し)をどれだけ早く捉えられるか、です。

このとき DNS は攻撃者にとって都合のよい通路になります。

- DNS(53番)は内部のほぼ全端末で常時開いており、止めると業務が壊れる。
- 宛先 IP とポートだけを見る L3/L4 の制御では、**正規の名前解決と悪用を区別できません**。
  「53番が開いているか」は分かっても「その問い合わせが何をしているか」は分からないからです。

そこで ChickenNet は、宛先ではなく **問い合わせの中身(QNAME / QTYPE)と発信元の振る舞い**
を見ます。これが本ドキュメントで言う「L7(アプリ層)検知」です。

## 何を検知するか

実装は [`dataplane/engine/lifeform/dns.py`](../dataplane/engine/lifeform/dns.py) の
`DnsAnomalyDetector`(ソケットを持たない純粋ロジック=単体テスト可能)です。
ブロックリストに**載っていない未知**を、署名ではなく振る舞いの点数で捕捉します。

| 兆候 | 観点 | 既定の扱い |
|------|------|-----------|
| トンネリング / 持ち出し | 異常に長い QNAME・高エントロピーのラベル・`TXT`/`NULL` の悪用 | 点数化して悪性で遮断(強制時) |
| ビーコン | 同一上位ドメインへ、毎回ユニークなサブドメインを連打 | 持続的に多いほど加点 |
| 内部偵察(AD) | `_ldap._tcp` / `_kerberos._tcp` / `_gc._tcp` 等の AD サービス照会 | **遮断せず可視化**(誤遮断回避) |
| 増幅・偵察寄り | `ANY` クエリ | 加点(単独では弱シグナル) |

判定は 3 段階で返します。

- `clean` … 通常の業務通信。
- `suspicious` … 兆候あり。**止めずにログへ残す**(可視化)。
- `malicious` … 強い兆候。**監査モードでは可視化のみ・強制モードでは遮断**。

### 「止める前に、まず見える化する」を既定に

エンタープライズでいきなり全遮断を始めると、正規業務を巻き込みます。そこで ChickenNet の
DNS L7 検知は **既定が監査(audit)**です。悪性と判定しても既定では遮断せず、根拠(signals)
付きでログに残します。運用で確信が持てた経路だけを `--enforce` で止める、という順序です。

とくに AD の SRV 照会(`_ldap._tcp` 等)は、ドメイン参加端末では正規にも頻出します。
本検知はこれを `malicious` に昇格させず、**強制モードでも遮断しません**(可視化のみ)。
正規の名前解決を壊さないための明確な線引きです。

## 使い方

```bash
# DNS フィルタ + L7 検知を単独起動(既定: 監査=止めず可視化)
python -m dataplane dns --listen 5335 --upstream 1.1.1.1:53

# 確信のある環境では強制(悪性判定を NXDOMAIN/sinkhole で遮断)
python -m dataplane dns --enforce

# 明示ブロックを併用(ブロックリストは L7 検知より優先)
python -m dataplane dns --block bad.example --block *.evil.example

# 信頼できる送信元(セキュリティスキャナ/監視)を L7 検知から免除
python -m dataplane dns --allow 10.20.0.0/24

# AD 前段で SRV 照会が騒がしい環境: 偵察フラグを無効化 + 通知集約を強める
python -m dataplane dns --recon off --dedup-window 120
```

## 利用者が選べる検知の挙動

環境に合わせて、検知の出方を選べます(設定は永続化されます)。

| 選択肢 | 既定 | 効果 |
|---|---|---|
| `--recon {alert\|off}` | `alert` | AD偵察(SRV: `_ldap._tcp` 等)を可視化アラートにするか、無視するか。ドメイン参加端末は SRV を日常的に引くため、DNS を AD 前段に置くと正常照会が大量に alert 化する。騒音が困る環境は `off` で発生源から黙らせる。 |
| `--dedup-window SEC` | `60` | 同一(送信元 × ドメイン × action)の通知連打を窓内で1件に集約(永続ログ・管理画面の氾濫防止)。`0` で無効。 |

> 補足: `--dedup-window` が集約するのは**永続ログ(`dns_threat_log.jsonl`)と管理画面**です。
> メトリクス(`recon`/`suspicious`/`blocked` 等)は累計として毎回カウントされます
> (集約の目的は『記録/表示の氾濫を抑える』であって、総量の可視性は保つ)。

> `--allow` は **L7 ヒューリスティック検知のみ**を免除します(誤検知抑制)。
> `--block` の明示ブロックリストは免除されません ―― 既知悪性ドメインは送信元に関わらず常に遮断。
> デコイ側の `--allow`([listeners.md](listeners.md))と一貫した運用です。

OS 非侵襲です。本機は DNS サーバを **立てるだけ**で、OS のリゾルバ設定
(`/etc/resolv.conf` や Windows のネットワーク設定)は変更しません。端末やルータの
参照先を本機へ向けることで効きます(透明・可逆)。

## 設計上の線引き(正直に)

- これは **検知のヒューリスティック**です。万能ではなく、誤検知・見逃しの両方が起こり得ます。
  既定を監査にしているのはそのためです。閾値は保守的に設定しています。
- **暗号化された DoH/DoT** はペイロードを直接見られないため、本機を経由しない DNS は対象外です。
- DGA や C2 ドメインの**網羅的なブロックリスト**は同梱しません(依存ゼロを維持)。
  既知の悪性ドメインは `--block` / 正規表現で運用側が登録します。
- **反撃はしません(防御専用)。** 検知しても遮断(NXDOMAIN/sinkhole)か可視化までです。
- **偽装フラッド耐性。** ビーコン検出の発信元追跡表は件数を上限(LRU)で縛るため、UDP の
  送信元IP偽装で大量の別アドレスを送られてもメモリは頭打ちになります。
- **遅い上流で詰まらない。** 1問い合わせを短命ワーカーで並行処理するため、上流リゾルバの
  解決が遅くても他クライアントのクエリは止まりません。同時数は上限で絞り、超過分は
  取りこぼします(DNS は再送されます)。

## 対象外と今後

本実装が触れるのは DNS(53番)の通路だけです。記事的な文脈で言えば「侵入後対策」のうち
**DNS の見える化という一部分**にあたります。Kerberos(88)/LDAP(389)/SMB(445) を含む
横展開全体の制御は本製品の範囲外で、それを丸ごと担うと主張することはしません。
将来、同じ「振る舞いで見る」考え方を他プロトコルの可視化へ広げる余地はありますが、
現時点では**未実装**です。誇張を避けるため、ここでは「DNS の部分適用」と明記します。
